# 07 · 采纳阶梯：从哪开始，怎么升级

不要一次到位。循环采纳是阶梯，每一级都要在前一级证明价值之后才爬。

---

## 五级阶梯

| 级别 | 名称 | 你能做什么 | 对应本框架 |
|---|---|---|---|
| **L0** | 草案 | 记录意图，还没运行 | 只写 `LOOP.md` |
| **L1** | 报告 | 分析、报告、更新状态。不改代码 | 本框架默认起点 |
| **L2** | 辅助 | 在 worktree 中提出修复，verifier 验证。合并在人工 | 加 `minimal-fix` + `loop-verifier` |
| **L3** | 无人值守 | 在明确边界内无人工监看运行 | 全部闸门 + 预算 + 熔断 |
| **L4** | 自喂循环 | 循环自己从状态发现下一个任务 | `feature_list.json` 作为任务源 |
| **L5** | 编队编排 | 多个循环并行，共享记忆层 | 多循环协调 + 优先级表 |

**大多数团队应该在 L1–L2 之间。** 只有当你已经有两周可靠的 triage 记录、验证器被证明有效、且 kill switch 演练过，才考虑 L3。

---

## 第一周：只报告

### 目标

不是自动化，是**校准 triage 的准确度**。

如果 triage 有一半是误报，L2 的自动修复会在错误的目标上浪费 token，并消耗人对系统的信任。信任一旦消耗，团队会静音机器人——那是所有升级机制失效的终点。

### 具体做法

1. **选一个痛点。** 找一个你每周至少手动做两次的重复任务：
   - 早上打开 GitHub 看新 issue、分诊、回复
   - 每次 PR 审查前跑 lint 和测试
   - 每天结束时更新进度文档

2. **装配脚手架。**
   ```bash
   node scripts/harness-stage.mjs . --upgrade --stage 1
   node scripts/harness-stage.mjs . --stage 1 --require   # 退出码 0 = 达成
   ```

3. **只跑 triage。** 每轮产出报告，写进 `STATE.md`，不改任何代码。

4. **每天读 `STATE.md`。** 判断：
   - 报告里的 High Priority 项，你同意吗？
   - 有哪些是噪声？
   - 有哪些它漏了？

5. **调整技能规则。** 把噪声类加入 `Noise / Ignore` 规则，把漏掉的信号加进 triage 检查项。

6. **一周后审计。**
   ```bash
   node scripts/loop-audit.mjs . --suggest
   ```
   目标：L1（分数约 40+）。

### 第一周明确不做

- ❌ 不自动修复
- ❌ 不自动合并
- ❌ 不启用写权限连接器
- ❌ 不提高 cadence 到 15 分钟以下

---

## 第二到三周：引入验证与隔离

### 前提

- triage 误报率 < 30%
- 每天读状态文件已成习惯
- 有一个明确、低风险的重复问题适合自动化

### 具体做法

1. **加 `minimal-fix` 技能。** 一个修复一个 diff，最多 5 个文件。

2. **加 `loop-verifier`。** 关键：**不同指令，最好不同模型**。
   - 执行者提示词："实现这个修复"
   - 验证者提示词："找出拒绝的理由，默认立场 REJECT"

3. **加 worktree 隔离。**
   ```bash
   git worktree add loop/ci-a1b2c3-fix-1 -b loop/ci-a1b2c3-fix-1
   ```

4. **加尝试上限。** 3 次，之后升级。用 `loop-ledger.json` 机械执行。

5. **加预算与熔断。** `loop-budget.md` + `scripts/ledger-check.mjs`。

6. **从最安全的模式开始。** 推荐顺序：
   - ✅ 依赖补丁更新（patch 级别，无 CVE 的）
   - ✅ CI 失败修复（明确、可验证）
   - ⚠️ PR 审查意见修复（需要理解意图）
   - ❌ 发布（永远人工）

### 第二到三周明确不做

- ❌ 不开启自动合并
- ❌ 不处理 major 版本依赖升级
- ❌ 不触碰拒绝列表路径
- ❌ 不并发运行多个循环

---

## 第四周起：考虑无人值守

### 前提（5 项全过）

- [ ] 技能中已包含拒绝列表
- [ ] 已关闭自动合并（默认就是关的：`defaults.auto_merge: false`），或配置了逐条允许列表 `loop-auto-merge-allowlist.md`（该文件尚未创建，只在真要开启自动合并时才需要）
- [ ] 已审计连接器权限范围
- [ ] 模式文档中已记录人工审核关卡
- [ ] kill switch 已记录并演练过

### 具体做法

1. **加成本可观测性。** 预算文档 + 运行日志 + `LOOP.md` 预算章节。缺任一项，L3 会被封顶到 L2。

2. **积累真实活动记录。** 至少跑完一个完整周期并提交运行日志。**结构性齐备不等于跑过。**

3. **扩大连接器权限。** 从只读 → comment + label。默认仍不允许 merge。

4. **逐步提高 cadence。** 先 1 天一次，观察一周，再考虑 6 小时、1 小时。

5. **建立多循环协调。** 加优先级表、`acting_on` 锁、跨循环收件箱。

---

## 反模式：不要跳级

| 跳级 | 后果 |
|---|---|
| L1 → L3 直接（第一天就自动修复 + 自动建 PR） | triage 未校准，在错误目标上烧钱；团队失去信任 |
| 没有 verifier 就 L2 | 自我验证，坏代码进 main |
| 没有预算就 L3 | 账单失控 |
| 没有 kill switch 就 L3 | 出问题只能看着它跑 |
| 没有 worktree 就并行 | 合并地狱 |

---

## 该选哪个模式开始

### 决策流

```
CI 经常红？                    → CI Sweeper
PR 长期停滞？                  → PR Review Triage
早上不知道该先做什么？           → Issue Intake + 每日概览
依赖/CVE 噪声多？               → 依赖补丁更新
合并后 TODO 累积？              → Post-Merge Cleanup
发布说明总过时？                → Release Drafter
```

### 成本感知推荐

| 情况 | 推荐 | 避免 |
|---|---|---|
| 业余项目/预算受限 | Release Drafter、Issue Intake (L1)、Post-Merge Cleanup | 每 5m 的 CI Sweeper、每 5m 的 PR Triage |
| CI 故障频发 | CI Sweeper，**15m+ 且带提前退出** | main 正常时仍每 5m 完整分诊 |
| 许多开放 PR | PR Review Triage 10–15m，先 L1 | 每次触发都跑 L2 修复 |
| 发布周 | 每天 Release Drafter | 无人值守依赖更新 + CI Sweeper 同时跑 |

### 起步配置速查

| 痛点 | 级别 | 节奏 | 上限 |
|---|---|---|---|
| CI 失败 | L2 | 15m | 3 次尝试 |
| PR 等待 | L1 监控 → L2 辅助 | 10–15m | 3 次尝试 |
| 每日"我该做什么" | **第 1 周 L1 仅报告** | 1d | — |
| 过时包 / CVE | L2 仅补丁 | 6h–1d | 禁止 major |
| 合并后 TODO | L1 非高峰 | 1d | 2 次尝试 |
| 发布说明 | L1 仅草稿 | 1d | — |

---

## 模式重叠规则

| 组合 | 规则 |
|---|---|
| CI Sweeper + PR Triage | CI Sweeper 负责失败的检查；PR Triage 不在同一小时内再修同一分支 |
| 每日概览 + 任何模式 | 概览负责报告，操作循环负责执行；L1 下概览不自动修复 |
| 依赖更新 + CI Sweeper | main 上 CI 出错时暂停依赖更新 |
| Post-Merge + PR Triage | Post-Merge 仅在非高峰运行 |
| Release Drafter + 任何模式 | 以读取为主，可安全并发；不应自动发布 |

---

## 成功指标（每一级都要定义）

| 级别 | 指标 | 目标 |
|---|---|---|
| L1 | triage 与人工判断的一致率 | > 70% |
| L1 | 从故障出现到人工知晓的时间 | 下降 |
| L2 | 无人工干预解决的失败百分比 | 上升 |
| L2 | 可审查→合并的平均时间 | 下降 |
| L2 | 内容仅为 "LGTM, loop handled the rest" 的人工评论数 | 上升（说明循环确实分担了工作） |
| L3 | 升级率 | 稳定且非 0 |
| L3 | 每周人工审查时间 | 下降 |
| 全部 | 每解决一个 work item 的 token 消耗 | 稳定或下降 |

**注意最后一条**：如果 token 消耗在上升，说明上下文管理出了问题，而不是"任务变难了"。

---

## 何时该停下来

循环不是越多越好。出现以下情况应该降速或终止：

- 连续两周成本 > 价值
- 团队把所有通知静音了
- 持续出现 S2 级失效（合并错误代码、告警疲劳）
- 维护循环本身的成本超过了它节省的时间

终止一个循环是**正常决策**，不是失败。写在 `stories/` 里，把经验留下来。
