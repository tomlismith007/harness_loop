# 11 · 三阶段 Harness：初始化 → 强化 → 巩固

本文档定义 harness 建设的三阶段递进模型。每个阶段有**明确的目标、判据、依据和退出条件**——不是"做得更好"，而是"这几项检查全过才算完成"。

用 `scripts/harness-stage.mjs` 机械判定当前阶段。

---

## 为什么要分阶段

**一次性把 harness 配齐是反模式。** 原因有三：

1. **无法判断哪一层出了问题。** 如果同时加上指令文件、验证命令、独立验证、事件接线，出了问题不知道是哪一层导致的。
2. **会跳过校准环节。** 独立验证的价值取决于 triage 的准确度。triage 一半误报时，自动修复会在错误目标上烧钱。
3. **无法量化每层的贡献。** 分层叠加才能做受控消融——一次移除一个子系统，看哪个移除造成的性能下降最大。

**分阶段的核心目的：让每一层的效果可观测、可归因。**

---

## 三阶段总览

| 阶段 | 名称 | 一句话目标 | 产物 | 对应等级 | 判据数 |
|---|---|---|---|---|---|
| **1** | 初始化 Init | 创建必要的 md 文件，让结构完整、下一会话可重启 | 10 个 md/json + init.sh | L1 | 10 机械 |
| **2** | 强化 Strengthen | 梳理并强化文件与机制，让验证真的有效、约束真的被强制执行 | 强化后的文件 + verifier + 熔断 | L2 | 6 机械 + 3 人工 |
| **3** | 巩固 Consolidate | 事件接上、循环跑起来、经验自己积累并转正为规则 | 事件接线 + 运行记录 + 转正规则 | L3 | 7 机械 + 1 人工 |

**关键区别**：

- 阶段 1 是**结构完整**——文件都在，但可能只是占位
- 阶段 2 是**机制有效**——验证真的能失败、约束真的被加载、熔断真的会触发
- 阶段 3 是**系统自转**——事件自动触发、教训自动积累、规则自动转正

**阶段 1 最容易被误判为完成。** 文件都存在、审计分数很高，但 `init.sh` 里还是占位命令、`loop-constraints.md` 的拒绝列表还是模板内容。所以判据里专门有"非占位"检查。

---

## 阶段 1 · 初始化（Init）

### 目标

创建必要的 md 文件，让 harness 结构完整、下一会话可重启。

### 判据（10 项，全部机械判定）

| # | 判据 | 检查方式 |
|---|---|---|
| 1 | 指令文件存在 | `AGENTS.md` 或 `CLAUDE.md` |
| 2 | 功能清单存在且合法 | `feature_list.json` 有非空 `features` 数组 |
| 3 | 状态文件存在 | `STATE.md` |
| 4 | 会话进度日志存在 | `progress.md` |
| 5 | 启动脚本存在 | `init.sh` |
| 6 | 循环配置存在 | `LOOP.md` |
| 7 | 约束文件存在 | `loop-constraints.md` |
| 8 | **init.sh 可执行且非占位** | 不含 "No package manifest detected"、"replace this line" 等占位符，且含 `set -e` |
| 9 | 五子系统都有最小工件 | instructions / state / verification / scope / lifecycle |
| 10 | 就绪度评分 ≥ 40 | `loop-audit.mjs` |

### 依据

| 来源 | 具体内容 |
|---|---|
| **LHE** 五子系统最小工件 | `AGENTS.md`（instructions）、`feature_list.json` + `progress.md`（state）、`init.sh`（verification）、feature 依赖与完成标准（scope）、`session-handoff.md`（lifecycle） |
| **LHE** 给地图不给手册 | `AGENTS.md` 是路由器，约 100 行；装不下就拆进 `docs/` |
| **LHE** 初始化是独立阶段 | 初始化产出基础设施而非业务代码；`init.sh` 的职责是"开工前确认环境健康" |
| **LEC** 脚手架产物 | `STATE.md` / `LOOP.md` / `loop-budget.md` / `loop-run-log.md` |
| **LEC** 第一周只报告 | 阶段 1 对应 L1，不自动修复、不自动合并 |

### 怎么执行

```bash
# 检测当前阶段 + 看差距
node scripts/harness-stage.mjs /path/to/repo

# 补齐阶段 1 缺失的文件
node scripts/harness-stage.mjs /path/to/repo --upgrade --stage 1

# 校验是否达成（CI 关卡）
node scripts/harness-stage.mjs /path/to/repo --stage 1 --require
```

### 退出条件

10 项判据全过。**但注意判据 8**——`init.sh` 必须是真实命令，不是占位符。

### 阶段 1 的常见错误

| 错误 | 后果 |
|---|---|
| 文件都建了，但 `init.sh` 是占位符 | 下一会话跑 `init.sh` 会失败或什么都不做，harness 形同虚设 |
| `AGENTS.md` 写成百科全书 | 违反"给地图不给手册"，agent 抓不住重点，且必然腐化 |
| `loop-constraints.md` 直接复制模板 | 拒绝列表不是本仓库的真实路径，等于没有约束 |
| 跳过阶段 1 直接进阶段 2 | 没有状态文件，verifier 无法判断改动的 scope |

---

## 阶段 2 · 强化（Strengthen）

### 目标

梳理并强化 harness 文件与机制，让**验证真的有效、约束真的被强制执行**。

阶段 1 让文件存在，阶段 2 让文件**起作用**。

### 判据（6 项机械 + 3 项人工）

**为什么人工判据占了一半**：grep 分不清「我们确实会这么做」和「有人抄过这句话」。阶段 1 的模板出厂时就带着"回退测试""NOT RUN"这些字样，如果拿它们当机械判据，阶段 2 会永远自动变绿——阶段闸门形同虚设。

| # | 判据 | 类型 | 检查方式 |
|---|---|---|---|
| 1 | 独立 verifier 已装到**可发现路径** | 机械 | 技能在 `.agents/skills/` 或 `.zcode/skills/`，不是在无人扫描的 `<repo>/skills/` |
| 2 | 约束技能已装到可发现路径 | 机械 | 同上——约束技能没被加载，约束就只是文档 |
| 3 | 熔断器就位 | 机械 | `loop-guard` 技能**且** `loop-ledger.json` 存在（熔断器要有账本可读） |
| 4 | 验证命令是真实的 | 机械 | `init.sh` 无占位符 |
| 5 | **拒绝列表已本地化** | 机械 | 与模板原文**有实质差异**（增删过路径）。纯 grep「有没有 .env」不算 |
| 6 | 就绪度评分 ≥ 58 | 机械 | `loop-audit.mjs` |
| 7 | **回退测试被实际执行过** | **人工** | 至少一次：新测试在修复前的代码上真的挂掉，且失败信息指出了错误的行为。命令与输出记进 `STATE.md` |
| 8 | **NOT RUN 声明被实际使用过** | **人工** | 至少一份验证报告把没跑的检查列为 NOT RUN（而不是省略） |
| 9 | triage 准确率 > 70% | **人工** | 跑满一周 L1 后逐条对比 |

**判据 1–3 检查的是"技能在不在 agent 会扫描的路径下"**，不是"文件在不在"。写在 `<repo>/skills/` 是个陷阱：文件看起来到位了，但没有任何 agent 会发现它——装在那里等于没装。

**判据 5 检查的是"有没有按本仓库调整"**，不是"有没有那句话"。模板自带 12 条通用拒绝路径，直接复制粘贴不算本地化。

### 依据

| 来源 | 具体内容 |
|---|---|
| **LHE** 受控消融测试 | 固定模型和任务，一次移除一个子系统，看哪个移除造成的性能下降最大。**只能回答"哪个组件最有价值"，不能回答"瓶颈在哪"**——瓶颈要靠失败归因 |
| **LHE** 三层终止校验 | 语法静态 → 运行时行为 → 系统级确认；层序规则：前一层失败不进下一层 |
| **LHE** 架构规则可执行化 | 把重复的 review 意见提升为机械规则；面向 agent 的错误信息要含 what / why / fix 三段 |
| **LEC** maker/checker 分离 | 写代码的模型给自己打分系统性偏高——这不是诚实问题，是生成模型的性质 |
| **LEC** 熔断阈值 | 同一错误 3 次 / 连续失败 5 次 / 总迭代 10 次 |
| **magpie** | 回退测试（证明测试能失败）、未跑必须写明、真机验证 |

### 为什么 verifier 是阶段 2 的核心

阶段 1 的文件让 agent **知道**该怎么做；verifier 让 agent **不能**糊弄过去。

没有 verifier，`AGENTS.md` 里的"完成定义"只是一句话——agent 可以声称自己完成了。有了独立 verifier，"完成"由外部证据判定。

**所以阶段 2 的第 1 项判据是硬性的**：没有 verifier，不允许进入阶段 3。这也是 `loop-audit.mjs` 把 L2 也要求 verifier 的原因。

### 怎么执行

```bash
node scripts/harness-stage.mjs /path/to/repo --upgrade --stage 2
```

补齐 `loop-guard`、`minimal-fix`、`loop-verifier` 技能。

然后**人工做两件事**（脚本无法代劳）：

1. **把拒绝列表改成真实路径**——模板里的 `.env`、`auth/` 是通用示例，要按本仓库调整
2. **跑满一周 L1，逐条对比 triage 判定与你的判断**

### 退出条件

6 项机械判据全过 **且** 3 项人工确认：

- 回退测试被实际执行过（有命令与输出为证）
- NOT RUN 声明被实际使用过
- triage 准确率 > 70%

**准确率不达标不要进入阶段 3。** 收紧 triage 技能规则，重跑一周。

### 阶段 2 的常见错误

| 错误 | 后果 |
|---|---|
| 装了 verifier 但和执行者是同一会话 | 结构性无效——自我验证 |
| verifier 指令是"确认它是对的" | 会系统性放行问题；必须改成"找出拒绝的理由" |
| 拒绝列表还是模板内容 | 真实的高危路径没被保护 |
| **把技能装在 `<repo>/skills/`** | 没有任何 agent 会扫描那个路径——文件到位了但从未被加载 |
| 跳过人工确认直接进阶段 3 | triage 误报率高，自动修复在错误目标上烧钱 |
| 只声明回退测试但从不执行 | 装饰性测试混进来 |

### 一个设计陷阱（本框架曾经踩过）

早期版本的阶段 2 判据用 grep 检查 `loop-constraints.md` 里有没有"回退测试""NOT RUN"这些字样。结果是：**阶段 1 的模板出厂时就带着这些文字，阶段 2 永远自动变绿，零工作量。**

这就是"检查声明"与"检查行为"的区别。修法是把这类判据降级为**人工确认**——脚本不再假装它能判断。判断力无法被 grep 替代，把它标成人工项比让它假绿诚实。

## 阶段 3 · 巩固（Consolidate）

### 目标

loop + harness 强化-巩固：**事件接上、循环跑起来、经验自己积累并转正为规则**。

前两个阶段让人机协作可靠；阶段 3 让系统在你不在时也可靠。

### 判据（8 项，7 项机械 + 1 项人工）

| # | 判据 | 检查方式 |
|---|---|---|
| 1 | **事件脊已接线** | `.github/workflows/` 有 loop 类 workflow，或 `LOOP.md` 声明了调度 |
| 2 | **LESSONS.md 有真实条目** | 含 `Seen N× (日期)` 形式的条目 |
| 3 | **运行日志有真实记录** | `## Log` 章节有含 `run_id` 的 JSON |
| 4 | 成本可观测性齐备 | 预算文档 + 运行日志 + `LOOP.md` 预算章节 |
| 5 | 多循环协调已声明 | `acting_on` 锁 + 优先级表 |
| 6 | **有教训已转正为硬规则** | `LESSONS.md` 的 Promoted 表有记录 |
| 7 | 就绪度评分 ≥ 78 | `loop-audit.mjs` |
| 8 | 至少跑过一个完整循环周期 | 人工确认 |

### 依据

| 来源 | 具体内容 |
|---|---|
| **LHE** 六原语 | automations（心跳）/ worktrees（隔离）/ skills（意图）/ connectors（触达）/ sub-agents（maker-checker）/ external state（跨轮记忆） |
| **LHE** 图工程 | 多循环在规模化下必然长出结构性问题（Goodhart / 向上盲区 / 循环冲突）；需要优先级、共享状态、回滚边 |
| **LEC** 事件驱动循环 | 事件型最省钱——没有事件就没有运行，空转成本接近零 |
| **LEC** 多循环优先级 | CI Sweeper → Merge Gate → PR Review Triage → Post-Merge → Release Drafter |
| **LEC** 成本可观测 | 80% 降级 report-only，100% 立即退出；高节奏循环必须提前退出 |
| **magpie** 夜审 | agent 每晚扫当天 commit，把教训写进 LESSONS.md |
| **magpie** 经验→规则棘轮 | 同一教训在 3 个不同日期出现 → 转正为硬规则 |
| **magpie** 成本分层 | 廉价模型做门卫，不相关信号直接丢弃 |

### 判据 6 是阶段 3 的验收核心

**「有教训已转正为硬规则」比「循环跑起来了」更能说明系统在工作。**

循环跑起来只是机械动作；教训转正说明系统完成了这个闭环：

```
发现返工 → 记进 LESSONS.md → 再次出现 → 第三次出现 → 转正为硬规则 → 下游强制执行
```

这个闭环跑通一次，才证明"经验→规则"的棘轮真的在转。**没有这个闭环，循环只是重复劳动，不会变好。**

### 怎么执行

```bash
node scripts/harness-stage.mjs /path/to/repo --upgrade --stage 3
```

补齐 `lesson-harvest`、`signal-gatekeeper`、`post-merge-cleanup`、`release-drafter` 技能，并复制事件接线到 `.github/workflows/`。

然后**人工配置**：

1. 设置 `LOOP_BOT_TOKEN`（独立机器人账号，最小权限，**不授予 merge**）
2. 确认 workflow 的触发条件符合你的实际需求
3. 接上 agent 平台消费 `.loop/queue/` 的产物

### 退出条件

7 项机械判据全过 **且** 人工确认跑过一个完整循环周期。

### 阶段 3 之后的维护

三阶段完成后不是结束，是进入维护循环：

| 周期 | 动作 |
|---|---|
| 每天 | 夜审自动跑，写 LESSONS.md |
| 每周 | 读一次运行日志的指标表；确认升级率非 0 |
| 每月 | 检查有没有教训该转正但没转正 |
| 每季度 | **做一次消融测试**：移除一个 harness 组件，跑基准任务，看分数是否下降。没下降说明该组件冗余（模型变强后假设过期） |

**季度消融是必须的。** LHE 的观察：每个 harness 组件都编码了"模型做不到什么"的假设，模型变强后假设会过期。不检查就会积累冗余约束——它们不提升可靠性，只消耗上下文。

## 阶段间的依赖关系

```
阶段 1 初始化
    │  文件存在 → agent 知道该怎么做
    ▼
阶段 2 强化
    │  verifier + 约束强制执行 → agent 不能糊弄
    ▼
阶段 3 巩固
    │  事件 + 循环 + 经验转正 → 系统自己变好
    ▼
维护（季度消融）
```

**依赖是单向的，不能跳过：**

| 跳级 | 后果 |
|---|---|
| 1 → 3 直接 | 没有状态文件与 verifier，循环在无约束状态下自动改代码 |
| 阶段 2 未过准确率就进 3 | triage 误报高，自动修复在错误目标上烧钱；团队失去信任后静音机器人，所有升级机制失效 |
| 阶段 3 未跑通转正就宣称完成 | 循环只是重复劳动，经验不积累，同一个错误反复出现 |

---

## 判据一览表

| 阶段 | 机械判据 | 人工判据 |
|---|---|---|
| 1 | 10 | 0 |
| 2 | 6 | 3（回退测试执行过 / NOT RUN 用过 / triage 准确率 > 70%） |
| 3 | 7 | 1（跑过完整循环周期） |

**人工判据不可跳过。** 脚本只能检查结构，不能判断"triage 是否真的准"或"循环是否真的有价值"。这两件事必须人看。

---

## 与等级的关系

| 阶段 | 对应等级 | 允许做什么 |
|---|---|---|
| 1 | L1 报告 | 分析、报告、更新状态。**不改代码，不合并** |
| 2 | L2 辅助 | 在 worktree 中提出修复，独立 verifier 验证。**合并仍需人工** |
| 3 | L3 无人值守 | 在明确边界内无人工监看运行 |

**等级是"允许做什么"，阶段是"建设到哪一步"。** 两者对应但不完全相同：一个仓库可能结构上够 L2，但因为 triage 未校准，实际只应跑 L1。

---

## 快速参考

```bash
# 我现在在哪一阶段？
node scripts/harness-stage.mjs /path/to/repo

# 补齐下一阶段
node scripts/harness-stage.mjs /path/to/repo --upgrade

# 补齐指定阶段
node scripts/harness-stage.mjs /path/to/repo --upgrade --stage 2

# CI 关卡：阶段 2 未达成则失败
node scripts/harness-stage.mjs /path/to/repo --stage 2 --require

# JSON 输出（供其他工具消费）
node scripts/harness-stage.mjs /path/to/repo --json
```

**退出码**：`0` = 报告模式或已达成；`2` = `--require` 且未达成。
