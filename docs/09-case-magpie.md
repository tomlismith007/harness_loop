# 09 · 案例：magpie 的全自动 loop 设置

> **来源**：一位实践者对其 magpie 项目 loop 设置的口述描述，加上三条 `/loop` 指令截图。
> **本文件性质**：对该设置的结构化提取，用于与 harness-loop 对照。不是本框架的规范，是外部参考实现。
> **标注约定**：**【述】** = 描述中明确给出；**【推】** = 我的推断，用于补全机制。
> **可信度**：口述二手信息，未独立核验仓库。数字与规则文本按原样保留。

## 0. 一句话概括

**magpie 的代码由 agent 编写、审查、合并、发布。**（LESSONS.md 第一句原文：`magpie's code is written, reviewed, merged and released by agents.`）

人只保留三件事：拍过的产品决定、安全闸门、社区建议的归属。写、审、合、发全交给 agent。

## 1. 文件分工：路由表模式

| 文件 | 职责 | 什么时候翻 |
|---|---|---|
| `AGENTS.md` | **纯路由表**，自己不写规则 | 开工前 |
| `docs/subsystems/` | 子系统改动规范 | 改子系统时 |
| `docs/code-standards.md`（案例仓库的文件） | 写码/审码标准（6 条验收 + 转正后的硬规则） | 写代码、审代码时 |
| `docs/contributors.md`（案例仓库的文件） | 社区 PR 审查规范 | 审社区 PR 时 |
| `LESSONS.md` | 错题本，agent 自己每晚写 | 夜间写入，白天读取 |

> 下表中除 `AGENTS.md` 外，`docs/subsystems/`、`docs/code-standards.md`、`docs/contributors.md` 都属于**案例仓库（magpie）**——本仓库（harness-loop）没有这些文件，也不在脚手架里生成它们。

**关键设计**：`AGENTS.md` 不承载规则，只承载「去哪找规则」。

```
改子系统      → docs/subsystems/
写代码、审代码 → docs/code-standards.md
审社区 PR     → docs/contributors.md
```

（以上三条目标文件均在**案例仓库**中，本仓库没有。）

**【述】** 灵感来源于 dsh（DeepSeek Harness 的「能力缝 + 插件化」思路）。**【述】** 在此之前，别人已经在自动 review 和管理了——也就是说路由表是后来加的优化，不是起点。

**【推】** 这个模式的价值在于：规则分散在各自的领域文档里，可以独立演进、独立审计新鲜度。`AGENTS.md` 只有一张表，永远不会腐化成「过去每次失败的垃圾场」。

## 2. 夜间复盘循环：LESSONS.md 机制（核心创新）

这是整套设置里最有价值的部分。

### 2.1 基本形态

| 属性 | 值 |
|---|---|
| 篇幅 | 479 行 |
| 作者 | agent 自己 |
| 写入时机 | **每天夜里** |
| 输入 | 当天全部 commit |
| 性质 | 错题本，不是文档 |

### 2.2 三个扫描目标

每夜把当天 commit 全过一遍，只关注三类场景：

1. **哪些修完又返工了** —— 同一个问题反复出现
2. **哪些压根不该合** —— 本不该进 main 的改动
3. **哪些验证做得太糙** —— 验证形式化、没真跑

### 2.3 每条记录的格式

```
一句规则 + 一段原因 + 证据（commit / issue 号）+ Seen N× (日期)
```

**实例原文**：

```
Reproduce the reporter's exact case, on the surface they use, before you
call it fixed. 834 came back 4 times (v0.1.920 → .925 → .931 → .938).
Each round fixed only the agent in the screenshot.
Seen 1× (2026-10-05).
```

中文：在称其为「修复」之前，先在报告者使用的那个界面上复现其具体案例。834 回归了 4 次（v0.1.920 → .925 → .931 → .938），每一轮只修了截图里的那一个 agent。

**【推】** 这条规则的成因值得注意：不是「要测试」这种泛泛要求，而是从**具体的返工模式**里提炼出的操作级指令——「用报告者那个界面」比「充分测试」可执行得多。

### 2.4 升级机制：经验 → 硬规则（最关键的一环）

```
同一条教训在 3 个不同日子的复盘里出现
        ↓
从 LESSONS.md 移到 code-standards.md
        ↓
从「经验」变成「硬规则」
        ↓
之后每个 PR 审查都要逐条对
```

**【述】** 已经有 **8 条**这么转正。

已转正的例子（**【述】**）：

| 规则 | 证据 |
|---|---|
| 同类的 bug 要一起修掉 | 10-05、10-06、10-07 各抓到一次 |
| main 上挂掉的测试就是马上要修的 bug | — |
| 合并前要写清楚跑了什么、在哪个 commit 上跑的 | — |

**【推】** 这个机制的精髓是**延迟提升**：一条经验只在第一次出现时不够格成为规则（可能是一次性的偶发），出现 3 次才说明它是系统性的。这避免了两种错误——过早立规矩（噪声变成制度），以及从不立规矩（经验永远停在笔记里没人执行）。

**`Seen 1×` 这一行是机制的支点。** 没有它，就无法机械判定何时该提升。

### 2.5 Done right 区

错题本也记录**做对的事情**，标成 `Done right`。agent 读到的除了「别这样」，还有「照这个来」。

**【推】** 只记录失败会训练出回避行为（不敢做决定）；同时记录成功案例给出了正例锚点。

### 2.6 起源数据（这套机制为什么被发明）

| 项 | 值 |
|---|---|
| 第一版 commit | `303819c5` |
| 第一版时间 | 10 月 6 日凌晨 3:10 |
| 引入前一天（10-05） | 发了 **168 个版本** |
| 第一版记录的数据 | 220 个 commit，约 170 次发版，其中约 **40 个在修当天或前一天刚发出的版本** |
| CI 状态 | 几乎每一轮都被下一次 push 取消 |
| 漏网的测试 | 一个只在 Linux 上挂的测试，从 v0.1.877 一路红到 v0.1.892，**没人发现** |
| 原文 | `294 tags in 51 hours left no run to finish.` |

**由此产生的第一条硬规则**：

> 打 tag 前，这个 commit 的 CI 必须跑完、全绿。被下一次 push 取消的不算。

### 2.7 效果

发版频率：**168 → 42 → 15 → 稳定在 15–26 之间**

**【述】** 中间没人开会，也没人发通知。夜审翻出问题 → 写进错题本 → 干活的 agent 读到 → 发版自然慢下来。

**【推】** 这是一个**自反馈闭环**：系统诊断出自己的病态行为（高频发版导致 CI 永远跑不完），把它写成规则，行为随之改变。没有人类干预。

## 3. PR 验收与合并

### 3.1 六条验收标准

**【述】** `code-standards.md` 里共 6 条，全过才能合并或发版。常规项（三平台编译、沙箱跑测试）未展开描述，三条不寻常的如下：

#### ① 回退测试（Red check）

> 把旧代码放回去，新写的测试必须**真挂**，而且挂得明明白白，指出是哪个行为错了。编译不过、测试被跳过都不算。

**【推】** 这是「验证你的验证器」——证明这个测试**有能力失败**。没有这一步，一个永远通过的测试和一个有效的测试在外观上无法区分。

#### ② 真实使用（真机验证）

> 改了哪家厂商的接入，就得拿真账号、真配置、真接口返回去验。**没实测过的功能，不许在上面接着开发，也不许跟用户说能用。**

**【推】** 这条同时切断了两个扩散路径：不能在上层叠功能（避免把未验证的假设固化成架构），不能对用户宣称可用（避免用户基于错误前提做决定）。

#### ③ 未跑必须写明

> `A check that wasn't run is listed as not run, never left out.`

**【推】** 这是**诚实性规则**，不是质量规则。它保证「缺口」是可见的：省略不写会让读者以为检查通过了，写明未跑则把决定权交还给读者。**这一条的成本极低，但防止的是一整类「沉默的失职」。**

### 3.2 PR 合并前评论格式

**【述】** 实际例子 #1339 的评论包含：

| 字段 | 含义 |
|---|---|
| `Red check` | 回退测试 |
| `Break check` | 故意改坏，看测试能不能抓到 |
| `Not run` | 真机没测就写没测 |

### 3.3 合并的机械安全措施

**【述】** 合并命令带 `--match-head-commit <审过的 sha>`。

**【推】** 这是**机械化的 TOCTOU 防护**（time-of-check to time-of-use）。审查期间如果有人又 push 了，head commit 变了，合并直接失败。这比「策略上要求重新审查」强得多——策略靠自觉，`--match-head-commit` 靠 git 本身拒绝。

## 4. 人机分工

### 人保留的三件事

| 领域 | 内容 |
|---|---|
| **产品决定** | `Don't reverse deliberate decisions` —— 滚动行为、按钮光标这类拍过板的决定，PR 不能改 |
| **安全闸门** | 风险检查一旦命中，等 maintainer 放行 |
| **社区建议归属** | 474 个 commit 标题里写着报告人来自 X 或 Discord（如 `JonahFu on X`、`Jeremy.Zhou on Discord`） |

### 分工原则

**人管方向、守闸门；agent 写、审、合、发。**

**【推】** 注意「社区建议归属」这条被归入人类职责，而不是 agent 职责。它表面上是记录工作，实质上是**信任与关系的维护**——把功劳归给人，是社区运营的一部分，不适合自动化。

## 5. 三条 `/loop` 指令（原文提取）

### 5.1 循环一：GitHub + Discord 巡检

> `/loop 盯一下 GitHub issues，仔细分析，看看哪些是值得修复和实现的，修复或者实现后记得发版和回复，如果不值得修复或者实现也要回复，如果是中转站的广告商，就统一回复：感谢关注，日后会出相关合作方案，敬请期待。而不能一股脑地把第三方中转站直接加到我们产品里面。也要盯一下GitHub的PR，然后你要认真的去review PR的每行代码、每个逻辑，你要把代码拉下来实际跑一下，验证一下是否没有bug。因为我怕有的人提的PR，是无脑用Coding Agent乱写的，自己都没测过。所以你要看一下他这个PR，是否有问题，确保一切都没有问题，且实际验证过之后也没有问题的话，你才能够去合并，否则你就去回复一下这个PR或者关掉 PR。另外还要监控一下 Magpie Discord Server 里用户的反馈，实时的加入讨论，如果有有价值的反馈和建议，就去做修复跟添加新的功能。如果值得进一步讨论，那就继续讨论。记得查看 Magpie Discord Server 里所有的 channel，一个都不能漏掉！记得在 Discord 里要真实地 at 人，而不是只叫名字，不然对方收不到你的消息！`

**提取的设定**：

| 项 | 设定 |
|---|---|
| 监听源 | GitHub issues、GitHub PRs、Discord 全部 channel |
| 判定 | 分三类：值得修复/实现、不值得、广告商 |
| 行动 | 值得 → 修复/实现 → 发版 → 回复；不值得 → **也要回复**；广告商 → 统一话术回复 |
| 产品边界 | **不能把第三方中转站直接加进产品** |
| PR 审查标准 | 逐行逐逻辑；**把代码拉下来实际跑**；验证无 bug 才合并；否则回复或关闭 |
| 明确的不信任 | 「怕有人无脑用 Coding Agent 乱写，自己都没测过」 |
| Discord 要求 | 所有 channel 一个不漏；**必须真实 @ 人**（只叫名字收不到） |

**【推】** 「不值得也要回复」是刻意设计：它保证每个报告者都收到回应，避免「石沉大海」导致的社区流失。统一话术处理广告商则把一类重复决策模板化，省 token 也省判断。

### 5.2 循环二：Twitter 巡检（含成本分层）

> `/loop 盯一下推特上关于 magpie 的反馈，如果是有价值的反馈，或者是真实可复现的bug，那么久去做实现或者修复。完毕后记得上线，上线后记得回复推特
>
> 你应该先用便宜的决策模型比如 jev 去判断推文是不是与 magpie 相关，是不是 magpie 的反馈，如果不是直接忽略不要把内容转发给你，不然太浪费 Token 了`

**提取的设定**：

| 项 | 设定 |
|---|---|
| 监听源 | Twitter |
| 判定 | 有价值 / 真实可复现的 bug |
| 行动链 | 实现或修复 → **上线** → 回复推特 |
| **成本分层** | **先用便宜的决策模型（如 jev）判断相关性**；不相关直接忽略，不转发 |

**【推】** 这是三条循环里唯一显式做**成本工程**的。设计要点：用一个廉价模型做**门卫**，只有相关的才送进昂贵的循环。「不要把内容转发给你」——说明是两级 agent，廉价模型在前。

### 5.3 循环三：清理 + 教训 + 黑名单

> `/loop 现在 magpie 完全是自动化更改代码和合并社区里的PR，你要定时清理一下屎山代码和恶意代码防止项目变得难以维护以至于变废，并总结出经验教训，比如哪些是不应该合并的哪些是验证不缜密的等等放到经验中防止以后的 agent 犯同样的错误，以及要把老是提低质量代码的人拉入黑名单`

**提取的设定**：

| 项 | 设定 |
|---|---|
| 前提认知 | 明确承认「现在是全自动改代码 + 合社区 PR」 |
| 任务一 | 定时清理**屎山代码**和**恶意代码** |
| 目标 | 防止项目变得难以维护以至于变废 |
| 任务二 | 总结教训：哪些不该合、哪些验证不缜密 → 写进经验 |
| 目的 | **防止以后的 agent 犯同样的错误** |
| 任务三 | 把**老是提低质量代码的人拉黑名单** |

**【推】** 任务二就是 LESSONS.md 的数据来源之一——这条循环**生产**教训，夜审循环**归集**教训。两者是同一个系统的两端。

**【推】** 黑名单是「按贡献者质量做准入控制」，属于自适应防御。风险点：误判会误伤正常贡献者，**【述】** 描述中未提及申诉或复核机制。

## 6. 这套设置的关键机制（分析）

把上面拆散的部分合起来看，真正让它运转的是七个机制：

### ① 经验 → 规则的棘轮

```
夜审发现返工  → 记一条（Seen 1×）
再次出现      → Seen 2×
第三次出现    → 转正进 code-standards.md → 之后每个 PR 逐条对
```

**价值**：经验不会永远停在笔记里；但也不会因为一次偶发就变成制度。**延迟提升**是这套设计最精巧的部分。

### ② 证据强制

每条教训都挂 commit 号和 issue 号。没有证据的观察进不了错题本。

**价值**：防止 agent 写出「要注意代码质量」这类无法执行的空话。

### ③ 回退测试（证明测试能失败）

新写的测试必须能在旧代码上**真的挂掉**。

**价值**：这是唯一能区分「有效测试」和「永远通过的装饰性测试」的机械手段。

### ④ 机械化的 TOCTOU 防护

`--match-head-commit <审过的 sha>`。

**价值**：把「审查后代码不能变」从策略变成 git 层面的硬约束。策略靠自觉，这个靠拒绝。

### ⑤ 未跑必须显式声明

`A check that wasn't run is listed as not run, never left out.`

**价值**：让缺口可见。成本极低，防止一整类沉默失职。

### ⑥ 成本分层

廉价决策模型做门卫，相关才送进昂贵流程。

**价值**：这是唯一能大规模降低 token 成本的架构手段——比调阈值、降频率都有效。

### ⑦ 自我诊断

CI 被取消这件事，是系统**自己发现**的（`294 tags in 51 hours left no run to finish`），并自己立了规则。

**价值**：系统能诊断自己的病态行为，而不只是执行外部指令。

## 7. 与 harness-loop 的对照

| 机制 | magpie | harness-loop 现状 | 差距 |
|---|---|---|---|
| **路由表 AGENTS.md** | 纯路由，规则在领域文档 | 已做（AGENTS.md 有去向索引） | ✅ 一致 |
| **教训积累** | `LESSONS.md`，夜审自动写，479 行 | 无。只有 `loop-run-log.md`（指标）与 STATE.md 的 Post-Run Critique（当轮） | ❌ **最大缺口** |
| **经验→规则升级** | 3 次出现 → 转正进 code-standards，8 条已转正 | 无机制 | ❌ **最大缺口** |
| **Seen N× 计数** | 有，是升级判定的支点 | 无 | ❌ |
| **Done right 记录** | 有 | 无（只记失败） | ❌ |
| **回退测试** | 强制：新测试必须在旧代码上挂掉 | verifier 检查「没有禁用的测试」，但不要求证明测试能失败 | ⚠️ 弱化版 |
| **真实使用验证** | 改厂商接入必须真账号/真配置/真接口 | 无对应要求 | ❌ |
| **未跑必须写明** | 硬规则 | verifier 报告跑过的，但无「必须列出未跑」的要求 | ⚠️ 弱化版 |
| **TOCTOU 防护** | `--match-head-commit` | 有 `acting_on` 锁，但无合并时的 commit 绑定 | ⚠️ 弱化版 |
| **成本分层** | 廉价模型门卫 | 只有百分比阈值（80%/100%） | ❌ |
| **清理循环** | 定时清屎山 + 恶意代码 | `post-merge-cleanup` 只扫技术债与文档缺口 | ⚠️ 部分 |
| **贡献者黑名单** | 有 | 无 | ❌ |
| **夜审循环** | 每晚复盘当天 commit | 无（只有事件驱动 + 每日 triage） | ❌ |

### 三个最值得补的缺口

**1. 教训累积与升级机制（LESSONS.md 模式）**

这是 magpie 设置里最独特、也最难自己想到的一环。当前 harness-loop 的 Post-Run Critique 是**每轮覆盖**的——填完就没了，不会累积。需要新增：

- `LESSONS.md`：只追加的错题本，每条含 `规则 + 原因 + 证据 + Seen N×`
- 夜审循环：定时扫当天 commit，找返工 / 不该合 / 验证太糙
- 升级判定：`Seen 3×` → 提示转正进 `loop-constraints.md` 或 `AGENTS.md` 的硬约束区

**2. 回退测试（Red check）**

把 verifier 的检查项从「没有禁用的测试」升级为「新测试必须能在修复前代码上失败，并指出失败的行为」。这一条能机械地筛掉装饰性测试。

**3. 成本分层**

在感知面加一层廉价门卫：先用低成本判断「这条信号是否相关、是否值得进入循环」，不相关直接丢弃，不送进昂贵流程。适用于高噪声源（社交平台、大型仓库的 issue 流）。

---

## 8. 可复制的最小版本

如果想在自己的项目里复现这套设置，最小可行集是：

| 步骤 | 做什么 |
|---|---|
| 1 | `AGENTS.md` 改成纯路由表，规则移到 `docs/` 下的领域文档 |
| 2 | 建 `LESSONS.md`，格式：规则 + 原因 + 证据 + `Seen N×` |
| 3 | 加夜审循环：定时扫当天 commit，三个扫描目标 |
| 4 | 定升级规则：`Seen 3×` → 转正进硬约束 |
| 5 | verifier 加两项：回退测试、未跑必须写明 |
| 6 | 合并命令绑定审过的 sha |

**不要一次全上。** 按 harness-loop 的采纳阶梯，先跑 L1 报告模式，确认 triage 准确后再加验证与隔离。
