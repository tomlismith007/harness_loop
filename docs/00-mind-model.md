# 00 · 心智模型：harness 是地基，loop 是运行层，事件是脊柱

这篇文档说明三者的边界、依赖关系和常见误用。读完之后你应该能回答：什么时候该修 harness，什么时候该修 loop，什么时候该修事件接线。

---

## 三层结构

```
┌─────────────────────────────────────────────────────────────┐
│  输入（Input）                                                │
│  GitHub issue / PR / CI 事件，或人写进 STATE.md 的待办         │
│  职责：决定"什么时候有什么工作"                                │
├─────────────────────────────────────────────────────────────┤
│  循环层（Loop Layer）— 六原语                                 │
│  Automations · Worktrees · Skills · Connectors ·             │
│  Sub-agents · External State                                 │
│  职责：决定"工作如何连续地发生"                                │
├─────────────────────────────────────────────────────────────┤
│  Harness 层（五子系统）                                       │
│  Instructions · Tools · Environment · State · Feedback       │
│  职责：决定"单次运行是否可靠"                                  │
└─────────────────────────────────────────────────────────────┘
```

**依赖方向是单向的**：harness 不牢，loop 只会把不可靠放大 N 倍；loop 不接事件，就只是在轮询空气。

---

## Harness 层：模型之外的一切

**定义**：harness 是模型权重之外的所有工程基础设施。

一个常用的对照：同一个模型、同一个任务，只有 harness 不同，成功率可以从 20% 到接近 100%。你没有换模型，你换的是 harness。

### 五个子系统

| 子系统 | 回答的问题 | 最小工件 | 缺失时的症状 |
|---|---|---|---|
| **Instructions** | 这是什么项目、怎么开始、规则是什么 | `AGENTS.md` | agent 选错包管理器、不遵守命名约定 |
| **Tools** | 它能做什么、不能做什么 | 权限配置 + 拒绝列表 | 要么什么都干不了，要么能改生产配置 |
| **Environment** | 环境如何复现 | `init.sh`、锁文件、版本固定 | "在我机器上能跑" |
| **State** | 现在做到哪了、下一步是什么 | `feature_list.json`、`STATE.md` | 每轮重新发现项目结构 |
| **Feedback** | 怎么知道做对了 | 验证命令、独立验证者（`/harness-loop` 第 4 步） | 宣称完成但测试红着 |

**投入产出比最高的通常是 Feedback。** 验证命令写得准，其他四个子系统的缺陷会自己暴露出来。

### 两个关键原则

**"仓库即规格"** —— agent 看不到的东西，实际上不存在。所有必要上下文必须落在仓库里：结构化的指令文件、显式的验证命令、清晰的目录组织。

**"给地图，不给手册"** —— `AGENTS.md` 应该是目录页，不是百科全书。约 100 行。装不下就拆进 `docs/`，让 agent 按需读取。单个巨型指令文件的问题不是"太长"，而是**无法机械检查覆盖度、新鲜度、归属和交叉引用**，所以必然腐化。

### 约束而非微观管理

好的 harness 用**可执行的规则**约束 agent，而不是逐条列举指令。

- OpenAI 的表述："enforce invariants, don't micromanage implementation"
- 实践含义：要求"数据在边界处解析"，而不是规定用哪个库
- 更强的形式：把每次代码评审发现的重复意见**提升为机械规则**。第一次发现 `renderer 不能直接 import fs`，第二次就加一条 lint 规则，第三次它就编译不过了

### 量化组件价值

用**受控消融测试**：固定模型和任务，一次移除一个子系统，看哪个移除造成的性能下降最大。下降最大的是当前最有价值的组件。

但注意：**消融只能告诉你"哪个组件最有价值"，不能告诉你"瓶颈在哪"。** 要定位瓶颈，必须先看失败记录并做归因——是任务不清、上下文不足、环境不可复现、验证反馈缺失，还是状态管理崩了。消融结果是佐证，不是结论。

## 循环层：六原语

| 原语 | 作用 | 没有它时的症状 |
|---|---|---|
| **Automations** | 心跳，让循环在你不在时启动 | 循环只是你手动跑的一次性运行 |
| **Worktrees** | 并行隔离，物理上防冲突 | 两个 agent 改同一文件，合并地狱 |
| **Skills** | 意图的持久记忆 | 每轮从零重新推导项目约定 |
| **Connectors** | 触达真实系统（issue tracker、CI、Slack） | 只能看文件系统，改完代码就停 |
| **Sub-agents** | 执行者/检查者分离 | 模型给自己打分，系统性偏高 |
| **External State** | 跨轮记忆 | 模型忘了一切，仓库没忘 |

### 最重要的结构选择：执行者 ≠ 检查者

**写代码的模型给自己打分是不可信的。**

这不是诚实问题，是生成模型的性质：它在生成过程中说服了自己这条路径正确，回头看时看到的是自己的推理过程，不是错误。一句话概括——**模型是自己输出的最佳辩护律师。**

推论：
- `/goal` 这类机制用**独立的全新会话**判断目标是否达成，而不是做事的那个会话
- 对抗式验证：为每个发现生成 N 个独立的怀疑者各自反驳，多数否决则杀死该发现
- 社区共识："你的团队里必须有人不信任你"

### 六原语怎么组合

最小可行循环 = **调度 + 一个技能（分诊）+ 一个状态文件**。

然后按需叠加：
- 开始改代码 → 加 worktree 隔离
- 自主行动 → 加子智能体验证
- 要推动 PR 而不只是建议 → 加连接器

**只在上一版本已证明价值并暴露失效模式之后，才加入新原语。**

## 事件或待办：把 loop 接到真实工作上

循环需要一个"什么时候做什么"的来源。有三种触发方式：

| 类型 | 触发 | 停止 | 适合 |
|---|---|---|---|
| **目标型**（`/goal`） | 你给一个目标 | 独立评估者确认达成，或达到最大轮次 | 有明确终点的复杂任务 |
| **时间型**（`/loop`、cron） | 定时 | 你手动停，或完成即退出 | 轮询状态、周期性检查 |
| **事件型** | 外部事件（PR 开了、CI 红了、issue 来了） | 处理完该事件，或达到重试上限 | 响应式工作流、CI/CD 集成 |

**事件型是最省钱也最贴合真实工作的**：没有事件就没有运行，空转成本接近零。

### 一条脊，而不是多条独立轮询

反模式是每个循环各自轮询自己的信号——CI Sweeper 轮询 CI，PR Babysitter 轮询 PR，Daily Triage 又轮询一遍全部。结果是重复劳动、状态不一致、互相冲突。

正确做法是**一个唯一的输入**（人写进 `STATE.md` 的待办；GitHub 事件是可选的补充）：

```
issue.opened ──▶ intake ──▶ triaged ──┐
                                      ▼
PR.opened ──▶ review ──▶ changes-requested ──▶ fix ──▶ verify ──▶ approved
                                      ▲                             │
CI.failure ──▶ classify ──────────────┘                             ▼
                                                                  gate
                                                                     │
PR.merged ──▶ post-merge ──▶ cleanup/debt ──▶ release draft ──▶ publish
```

每个事件产生一个 **work item**，work item 沿状态机流动，每一跳都有技能、证据和闸门。

### 事件驱动的关键判定：这件事有终点吗？

- **有终点** → 目标型。`/goal "所有测试通过，零 lint 警告"` 会在达成后停止。
- **没终点，只是持续观察** → 时间型。`/loop 15m 检查 CI 是否坏了` 每轮独立。

常见错误：把该用目标型的东西塞进时间型。`/loop 10m "继续实现支付系统"` 是错的——时间型循环每轮独立执行同一指令，不记得上次做到哪了，你会一遍遍从同一个起点开始。

## 什么时候修哪一层

| 症状 | 该修哪一层 |
|---|---|
| 同一个任务，换会话就做不好 | **Harness** — 状态没落盘，或指令文件缺失 |
| 每轮都要重新解释项目约定 | **Harness** — Instructions 子系统 |
| agent 宣称完成但测试红着 | **Harness** — Feedback 子系统，加独立 verifier |
| agent 改了不该改的文件 | **Harness** — 拒绝列表没进指令，或 verifier 没检查 scope |
| 循环从不自己启动 | **Loop** — 没有 automation |
| 两个 agent 改同一文件冲突 | **Loop** — 没有 worktree 隔离 |
| 循环每轮从零开始，不记得上次 | **Loop** — 没有 external state |
| 循环自我验证后放了坏代码进 main | **Loop** — 没有 maker/checker 分离 |
| 循环空转烧钱 | **Loop** — 没有提前退出条件 |
| 循环不知道该响应什么 | **输入不明确** — 没有唯一的待办来源 |
| 同一件事被重复处理 | **输入不明确** — `STATE.md` 没有单一活动项 |
| 事件发生了但没人处理 | **输入不明确** — 没有 `/harness-loop-issue` 或人工待办 |

## 三条不可协商的规则

1. **写代码的人不能验证自己的代码。**
2. **同一事项最多尝试 3 次，之后升级给人。**
3. **没有机器可判定的停止条件，就不算一个循环。**

这三条是后面所有闸门、预算、熔断机制的来源。

## 四个沉默成本

循环跑起来后不会立刻看到问题。这四个成本在积累，等你注意到时可能已经付了很多。

| 成本 | 表现 | 对策 |
|---|---|---|
| **验证债** | "看起来没问题" 取代了 "确认正确" | 停止条件必须机器可判定 |
| **理解腐化** | 交付变快但没人能解释最近的变更 | 非平凡 PR 必须人工审查；每周读一次循环摘要 |
| **认知让渡** | "循环会处理"——不再对正确性形成判断 | 用循环放大思考，不是替代思考 |
| **token 爆炸** | 每轮累积上下文，prompt 规模近似二次增长 | 从第一个循环就做上下文管理 |

关于认知让渡，Osmani 的表述值得记住：**两个人可以搭出一模一样的循环，得到相反的结果。一个人用它在自己懂的工作上加速，另一个人用它逃避理解工作。循环分不清这两者。你分得清。**
