# 05 · 失效模式：症状、原因、对策

循环出错时看这篇。按严重程度分级：**S1 烦人**（浪费 token，不影响用户）、**S2 有害**（合并错误代码、告警疲劳）、**S3 严重**（安全问题、数据丢失、生产事故）。

---

## 一、循环行为类

### 1. 无限修复循环（S2）

| | |
|---|---|
| **症状** | 同一 PR / CI job 自动尝试修复 5 次以上仍不收敛 |
| **原因** | verifier 太弱或与执行者同会话；误判根因只修表象；把不稳定测试当回归 |
| **对策** | 硬性限制尝试次数（3 次）后升级；独立验证模型；triage 阶段识别 flake 并隔离而非改代码；状态文件记录尝试次数 |

**根因识别**：如果第 2、3 次尝试的错误文本与第 1 次相同（归一化后），说明根本没有触及根因。熔断器的 `stagnation` 检测就是为此设计的。

### 2. 验证者作秀（S2）

| | |
|---|---|
| **症状** | verifier 声称 approve，但 CI 失败或代码审查发现明显缺陷 |
| **原因** | 提示词过于含糊（"looks good"）；verifier 没跑测试；verifier 与执行者同模型同上下文 |
| **对策** | verifier 必须跑测试和 lint 并报告输出；使用不同指令（"find reasons to reject"）；无人值守循环给 verifier 用更强模型 |

**判定信号**：verifier 的输出里有没有命令和输出片段。没有就是作秀。

### 3. 越界 / 范围错误（S2）

| | |
|---|---|
| **症状** | 循环重构无关模块、"修复"设计问题、改拒绝列表路径 |
| **原因** | 执行者段落过宽松；无路径允许/拒绝列表；triage 把架构工作列入 High Priority |
| **对策** | 技能中强制执行拒绝列表；"尽可能小的差异" + verifier 检查被改动文件；triage 只报告信号不创造事项 |

**量化信号**：单次修复改动 > 5 个文件，或 diff 中含与 work item 无关的文件。

### 4. 并行冲突（S2）

| | |
|---|---|
| **症状** | 两个子智能体编辑相同文件，造成合并冲突和状态损坏 |
| **原因** | 未用 git worktree 隔离；两个循环无协调处理同一 PR |
| **对策** | 所有编辑代码的子智能体用独立 worktree；`STATE.md` 的 `acting_on` 锁定或排队 |

### 5. 升级失败（S2）

| | |
|---|---|
| **症状** | 循环陷入重试，人工始终没收到通知 |
| **原因** | 未实现最大尝试次数限制；升级只写入无人读取的状态文件 |
| **对策** | 升级时通过连接器发提醒；`STATE.md` 用 `High Priority (waiting on human)` 区段；条目停留 > 24h 则告警 |

**最隐蔽的变体**：升级机制在技术上存在（状态文件里有一行），但没人会读那个文件。**升级必须有推送通道。**

## 二、状态类

### 6. 状态腐化（S1）

| | |
|---|---|
| **症状** | `STATE.md` 引用已合并 PR、已关闭工单或陈旧分支 |
| **原因** | 运行结束无清理步骤；运行开始不读状态；多循环无结构规范写同一文件 |
| **对策** | 每轮清理已关闭/已合并条目；记录 `Last run` 时间戳并用实时 API 验证 ID；每模式一个状态文件或清晰分区 |

### 7. 理解债务螺旋（S2）

| | |
|---|---|
| **症状** | 交付变快但没人能解释近期变更；代码审查沦为走过场 |
| **原因** | 人工不再阅读循环输出；在扩大允许列表上启用自动合并；无每周人工总结 |
| **对策** | 非简单 PR 必须人工审查；负责人每周读一次循环摘要；自动合并严格限制在真正简单路径 |

### 8. 认知让渡（S2）

| | |
|---|---|
| **症状** | "循环会处理"——不再对正确性或设计形成判断 |
| **原因** | 成功指标是数量不是质量；中等风险工作无人工关卡 |
| **对策** | 每个模式明确设人工关卡；成功指标 = 守住质量标准前提下节省的时间 |

> 两个人可以搭出一模一样的循环，得到相反的结果。一个人用它在自己懂的工作上加速，另一个人用它逃避理解工作。循环分不清这两者。你分得清。

## 三、成本类

### 9. Token 消耗（S1）

| | |
|---|---|
| **症状** | 账单激增；循环针对空/充满噪声的分诊结果跑完整子智能体链 |
| **原因** | 不足一分钟 cadence 调用重型子智能体；监视列表为空无提前退出；瞬时 API 错误重试整个流水线 |
| **对策** | 先跑低成本 triage，仅有可操作条目才启动子智能体；无监视对象时提前退出；设每日 token 预算 |

**数量级参考**：15 分钟 cadence 的空转一天是 96 次。若每次空转 5k token，纯浪费 480k。这就是为什么高节奏循环**必须**有提前退出。

### 10. 通知疲劳（S1）

| | |
|---|---|
| **症状** | Slack/邮件每 5 分钟提醒，团队最终静音机器人 |
| **原因** | 每轮都通知而非仅*可操作*发现；triage 对 "High Priority" 门槛太低 |
| **对策** | 仅在需要人工决策时通知；仅报告循环用摘要模式；收紧 High Priority 规则 |

**静音是失败的终点**：一旦团队静音了机器人，所有升级机制都失效了。

## 四、结构性失效（规模化后才显现）

这三条来自图工程的观察——**单循环在规模化下必然长出结构性问题**，因为判定者与被判定者共用一个大脑。

### 11. Goodhart 失效（S2）

| | |
|---|---|
| **症状** | 指标被推爆后不再度量原意。工单解决率上升，但续约流失翻倍——bot 学会了关单：推诿、劝阻追问、把未解决问题标为已解决 |
| **原因** | 优化的是指标而不是目标；指标的定义者与优化者是同一个 |
| **对策** | 加 anchor：把循环钉回真实业务结果（人工抽检、ground-truth 数据集） |

### 12. 向上盲区（S2）

| | |
|---|---|
| **症状** | 循环内参考值神圣不可质疑。恒温器不会问 68°F 是否正确 |
| **原因** | **单循环结构中不存在能提出这个问题的位置** |
| **对策** | 引入拥有全新上下文的独立节点，专门质疑前提 |

### 13. 循环冲突（S2）

| | |
|---|---|
| **症状** | 独立循环互相拆台（响应速度侵蚀彻底性；增长侵蚀质量），各自仪表盘健康而系统整体抽搐 |
| **原因** | 每个循环局部最优，无全局协调 |
| **对策** | 明确优先级表 + `acting_on` 锁 + 跨循环收件箱 |

## 五、诊断流程

循环行为异常时，按顺序问：

```
1. 事件到达了吗？
   → 查 workflow 日志 / webhook 投递记录
   → 否：接线问题，不是 agent 问题

2. 路由正确吗？
   → 看 STATE.md 的 High Priority 是否只有一项
   → 否：待办来源不唯一

3. 约束加载了吗？
   → 看运行日志开头有没有 "Constraints loaded from loop-constraints.md: N rules active."
   → 否：技能没读约束文件

4. 预算内吗？
   → node .claude/skills/harness-loop/scripts/ledger-check.mjs
   → 否：应该降级或退出，检查闸门实现

5. 尝试了几次？
   → 看 loop-ledger.json
   → >= 3：应该已升级，检查熔断器是否工作

6. verifier 真跑了测试吗？
   → 看 verifier 输出有没有命令 + 输出片段
   → 否：验证者作秀，改 verifier 提示词

7. 错误签名是否重复？
   → 归一化后比较第 1 次与第 N 次的 error
   → 是：根因未触及，应该升级而不是重试

8. triage 准确吗？
   → 看 STATE.md 的 Post-Run Critique 与人工判定
   → 误报 > 30%：收紧 triage 规则，不要进入 L2
```

## 六、熔断器规格（`.claude/skills/harness-loop/scripts/ledger-check.mjs`）

### 检测顺序

先报最具体可行动的：

```
1. stagnation     — 同一错误签名出现 N 次（默认 3）
2. no-progress    — 连续失败 M 次（默认 5）
3. token-budget   — 超预算
4. max-iterations — 总迭代上限（默认 10）
```

### 错误签名归一化

抹掉以下内容后比较，使"同一个错误"能被识别：

- ISO 时间戳
- 十六进制地址
- 路径（折叠为 basename）
- 行列号
- 位置/时长类数字（`line 42`、`500ms`）

**不抹掉**退出码、HTTP 状态码、断言期望值等裸数字：把 `exit code 1` 与 `exit code 2`
归一成同一个签名，会让根因不同的失败在第 3 次被误判为停滞。

### 退出码

| 码 | 含义 | 动作 |
|---|---|---|
| `0` | 继续 | 可以重试 |
| `1` | 参数错误 | 命令写错了，不是通过 |
| `2` | 停止 | 不再重试，写升级条目，退出循环。账本缺失或非法 JSON 也返回 2 |

### 规则

- **绝不为了继续循环而放宽阈值。** 升级是功能，不是失败。
- **绝不编辑账本来隐藏重复错误。**

## 七、反模式清单（启用前避免）

| # | 反模式 | 正确做法 |
|---|---|---|
| 1 | 由同一智能体实现并验证 | 独立 verifier，默认立场 REJECT |
| 2 | 没有尝试次数上限（"Keep trying until CI is green"） | 硬性上限 3 次 → 完整上下文写入状态并升级 |
| 3 | triage 输出含糊（大段叙述） | 结构化章节、每条目单行、明确 `Suggested loop action` |
| 4 | 在 L1 质量达标前启用 L2 自动修复 | 第一周 L1 仅报告，先衡量 triage 准确性 |
| 5 | 共享状态却没有结构规范 | 每模式一个状态文件，或清晰分区 + 清理规则 |
| 6 | MCP 拥有无限制写入权限 | L1 只用只读连接器 |
| 7 | 没有紧急停止开关 | 在 `STATE.md` 或 `loop-constraints.md` 写独占一行的 `loop-pause-all` |
| 8 | 用代码修复间歇性故障 | 分类 → 隔离或重试策略 → 升级环境故障 |
| 9 | 没有路径许可清单却自动合并 | 明确允许列表（`loop-auto-merge-allowlist.md`，尚未创建——只在真要开启自动合并时才需要；框架默认不自动合并，所以当前安全）；拒绝列表路径人工合并 |
| 10 | 没有运行日志（只有 STATE.md） | 追加到 `loop-run-log.md` |
