00

三层结构：谁负责什么

这三层是理解全部流程的前提。下层不稳，上层只是把不可靠放大；上层没有运行器， 事件就止于“任务已交付”。

EVENT SPINE
事件脊：决定“什么时候有什么工作”

GitHub 事件（issue / PR / CI / tag）进入 workflow → 被消毒 → 调 event-router.mjs 得到 phase、skills、gates → 写成 .loop/queue/<item>.json → 作为 artifact 交付。 机制

LOOP LAYER
运行层：决定“工作如何连续发生”

harness-loop 技能按 8 步跑一轮：退出检查 → 约束 → 路由 → 锁 → 预算 → 派发 → 闸门 → 状态。它不执行具体动作，只决定派发谁、何时停、何时交给人。 约定（技能由 agent 执行）

HARNESS
地基：决定“单次运行是否可靠”

AGENTS.md（指令）、STATE.md + feature_list.json（状态）、 init.sh（验证入口）、loop-constraints.md（范围底线）、 loop-verifier（独立检查者）。

先记住这条边界

本包不含 agent 运行器。workflow 只做“感知 + 判定 + 记账”， 真正的修改与验证需要外部平台消费队列产物。没有平台时，循环停在 fix-proposed——这是合法结局，不是“已经自动修好了”。 未接线

01

装配：从空仓库到可运行

入口只有一个：harness-stage.mjs。它先审计目标仓库，算出当前阶段， 再按 --upgrade --stage N 补齐产物。阶段驱动技能只在包仓库运行。

① 检测 node scripts/harness-stage.mjs <repo> → 跑 loop-audit 评分，逐条执行阶段判据，输出当前阶段与差距。只读。
↓
② 补齐 node scripts/harness-stage.mjs <repo> --upgrade --stage N。跳级会被拒绝（阶段 3 要求 1、2 已完成），--force 是显式逃生门。
↓
③ 校验 --stage N --require：未达成退出码 2，可直接做 CI 关卡。

阶段判据在检查什么

  • 阶段 1（8 项机械）：指令/状态/进度/约束文件存在；feature 有可判定完成标准；init.sh 真的执行并退出 0；就绪度 ≥ 40。
  • 阶段 2（6 机械 + 3 人工）：verifier / 约束技能在可发现路径；熔断器有非空账本；拒绝列表已本地化；回退测试、NOT RUN、triage 准确率由人确认。
  • 阶段 3（7 机械 + 1 人工）：事件真的接线（仓库事件 + 调 router + 消费结果）；LESSONS 有真实条目；run-log 有记录；有教训已转正；跑过一个完整周期由人确认。
02

事件入口：workflow 实际做什么

每个 workflow 结构相同：消毒输入 → 调路由 → 检查锁 → 落盘 work item → 上传 artifact。 它不修改代码，也不做验证。

GitHub 事件到达issues / pull_request / pull_request_review / check_suite / workflow_run / push:tags / schedule
↓
确定事件名与 item事件字段经 env: 传入，再用 tr -c 消毒；绝不把 ${{ github.event.* }} 拼进 run: 正文（分支名可注入）。item 形如 issue-1 / pr-2 / ci-<sha>-<branch>。
↓
预算与 kill switchbudget-check.mjs --pattern <id> --json。读不到结果就拒绝运行（fail-closed）；mode=exit 直接停。
↓
路由event-router.mjs --event <e> --item <i> --target <branch|pr> → route.json。输出 phase / skills / level / gates / next，可能带 conflict: lock-held。
↓
锁检查与落盘jq -r '.conflict'；lock-held 时跳过写队列。否则写 .loop/queue/<item>.json（id / event / phase / branch / sha / created_at）。
↓
交付actions/upload-artifact@v4。runner 文件系统是临时的——不上传就随 job 消失。

03

运行时主循环：harness-loop 的 8 步

这是“一轮”的完整路径。第 0 步的退出检查放最前，因为它是高节奏循环唯一的经济性来源： 没有待办就不该启动任何子智能体。

0

退出检查 机制

按顺序检查，任一命中即退出，不继续：

  • budget-check --pattern <id>：退出码 3 = 立即停（暂停或 ≥100%）；report-only = 不派发执行者。
  • hasEventWiring()：没有“仓库事件 + 调 router + 消费结果”的 workflow → no-wiring 退出。
  • queue-read --json：读 .loop/queue/，为空回落到 STATE.md 的 High Priority；无待办 → no-op 退出（<5k token）。
EXIT no-wiring · 项目未到阶段 3 EXIT no-op · 队列为空 EXIT exit · 暂停或超预算
1

加载约束 约定

读 loop-constraints.md，输出 Constraints loaded … N rules active.。每条规则标了 机制 或 约定，后续动作前对照相应章节复核。

2

路由事件 机制

event-router.mjs --event <e> --item <i> --target <branch|pr>。得到 phase / skills / level / gates / next。事件不在表里 → 记 Watch List，不自创流程。

--target 不可省：它是锁键（acting_on），不是 work item id。省掉后不做冲突检测，锁静默失效。

3

检查冲突锁 机制

读 STATE.md 的 Active 表：若另一循环的 acting_on 等于本次目标 → 跳过，记 outcome: no-op（原因 lock-held）；否则写入本轮 acting_on。

锁键统一为分支名或 PR 号。item 与 acting_on 混用会让锁永远不触发。

SKIP lock-held · 本轮 no-op
4

预算分级 机制

<80% 正常，可派发执行者；≥80% report-only：不派发执行子智能体，只产出报告。阈值只在 budget-check.mjs 一处定义。

5

派发技能 约定 本包无运行器

顺序固定：先跑感知类 triage（便宜）→ 只有产出可操作条目才派发 minimal-fix → 修复后必须跟独立实例的 loop-verifier。

代码改动必须在独立 worktree：worktree.mjs create --event <e> --item <i> --attempt <n>，命名 loop/<event>-<item>-attemptN；REJECT 后 discard 连分支一起删。

没有外部平台时，这一步不会真正发生；循环停在 fix-proposed。

6

执行闸门 机制

gate-check.mjs，六个不可省参数：@ 清单前缀、--reviewed-sha + --head-sha、--red-check、--evidence-file（approve 时）、--not-run、--constraints-root。详见下一节。

0 proceed · 继续 2 escalate · 写升级条目 3 exit · 立即停止
7

熔断检查 机制

每次尝试追加到 loop-ledger.json，重试前跑 ledger-check.mjs --ledger loop-ledger.json。退出码 2 → 停止，不再重试。

STOP stagnation / no-progress / no-ledger / placeholder-ledger …
8

写状态 机制

更新 STATE.md（Active / High Priority / Watch List / Last run）；有代码改动则更新 feature_list.json；追加一行 JSON 到 loop-run-log.md；清理已关闭条目；填写 Post-Run Critique，必须产出一项具体调整。

不写状态的运行等于没跑。

一轮只允许这六种结局

outcome含义是否指向人
no-wiring项目还没接事件脊，第 0 步退出是（推进阶段，不是故障）
no-op无待办或锁被持有，提前退出否
report-only产出报告，未改代码否

退出码的语义

0 = proceed / report-only 1 = 参数错误（闸门没跑，不是通过） 2 = escalate 给人 3 = 立即停止

调用方必须把 1 当成“我没问对问题”，绝不能当成“闸门通过了”。 merge-gate.yml 用 set +e 接住 2，让 PR 评论与失败判定仍能执行； 只有 1 会让 job 直接失败。

05

预算与急停：budget-check 的真实算法

预算是估算，不是精确计量。但它必须有一个真实入口——否则“80% 降级”只是文档里的一句话。

输入

  • loop-budget.md 的 Daily Limits 表：按行名（自然写法与连字符写法都认）建索引。
  • loop-run-log.md：只解析单行 JSON；只算 run_id 是今天、且 pattern 匹配的 tokens_estimate。
  • STATE.md / loop-constraints.md：独占一行的 loop-pause-all。

判定顺序

  1. 暂停 → exit
  2. 查不到该循环的上限 → exit（没有上限就没有刹车）
  3. ≥ 100% → exit
  4. ≥ 80% → report-only
  5. 否则 normal

退出码：0 = normal / report-only；3 = exit。

解析上限resolveCap(caps, pattern) 返回 cap 与 source：exact（自己有行）/ alias:<表名>（借来的）/ null（没有）。借来的上限在输出里可见，不静默回退。
↓
汇总今日花费sumTodaySpend()。文档明确要求一条记录一行；多行 pretty JSON 会被算成 0——这一点有断言守着。
↓
决定模式decide()：暂停 → 无上限 → 100% → 80% → normal。阈值只在 DEFAULT_THRESHOLDS 一处。

已知限制：花费数字目前是 0

只有 daily-triage / lesson-harvest 会写 run-log，而且写的是固定估算值； 其余 6 个 workflow 不写。runner 文件系统又是临时的，写入需要先决定持久化方式 （提交分支 / PR 评论 / 平台写）。立即生效的是 kill switch 与“无上限即退出”； 百分比要等持久化方式定下来才有意义。未接线

错误签名怎么归一化

抹掉 ISO 时间戳、十六进制地址、路径（折叠为 basename）、行列号，以及明确是位置或时长的数字。 不再把退出码、HTTP 状态码、断言期望值全部抹平——否则“500 服务端错误 → 404 路由缺失 → 超时” 三种根因完全不同的失败会在第 3 次被误判为同一个错误。

07

验证契约：verifier 写什么，闸门读什么

verdict 是断言，不是证据。这条链路的价值全在“生产者与消费者对同一种格式达成一致”。

loop-verifier 产出

以带标记的 PR 评论发布，第一行必须是：

<!-- loop-verifier-report -->
## Verdict: APPROVE | REJECT | ESCALATE_HUMAN
Commit: <被验证的 head sha>

### Evidence
- Tests: `npm test` → PASS
- Red check: PASS | FAIL | NOT RUN — 说明
- Real-use validation: PASS | FAIL | NOT RUN — 说明
- Lint: `npm run lint` → PASS
- Scope check: PASS | FAIL — 说明
- Denylist check: PASS | FAIL
- Files changed: N

### Checks not run
- <检查项> — 原因

merge-gate 怎么取

  1. 取 PR 的 headRefOid 作为 head。
  2. 取最后一条 review，要求它就是 APPROVED；取它绑定的 commit 作为 reviewed。没有批准时绝不回退成 head。
  3. 只接受机器人账号（LOOP_BOT_LOGIN，默认 loop-bot）发的带标记评论；PR 作者伪造不了。
  4. red-check 状态从 PR 正文的独占行 red-check: pass|fail 读；读不到就是 not-run。
  5. 把 verdict、两个 sha、red-check、证据文件一起交给 gate-check；调用方不改写闸门结果。
证据文件进入 gate-check解析 verdict 行与检查行；接受带命令的 `cmd` → PASS，也接受 verifier 模板里不带命令的 Red check: FAIL。箭头 -> 与 → 等价。
↓
交叉校验报告说 APPROVE 但有 FAIL → 拦；全 NOT RUN → 拦；### Checks not run 缺失 → 拦；证据里的 NOT RUN 没列进该节 → 拦；报告 Commit: 与 head 不符 → 拦。
↓
输出decision、命中的 gate、可读的 reason、checks_not_run、next。升级与通过都带下一步动作。
08

状态回写：下一轮凭什么能接上

模型会忘，仓库不会。状态文件是跨会话连续性的唯一载体；写入规则本身也是机制的一部分。

STATE.md

活状态，每轮读写。

  • Last run：时间戳
  • High Priority：正在做 / 等人
  • Active：work item + acting_on 锁
  • Watch List：观察，不行动
  • Human Inbox：模糊 / 跨循环
  • Post-Run Critique：每轮必须产出一项调整

不得包含任何凭据；历史不堆回本文件。

loop-run-log.md

只追加，一条记录一行 JSON。

{"run_id":"…","pattern":"ci-sweeper",
 "event":"check_suite.completed:failure",
 "item":"ci-a1b2-main","level":"L2",
 "duration_s":45,"items_found":4,
 "actions_taken":1,"escalations":0,
 "tokens_estimate":52000,
 "outcome":"fix-proposed"}

多行格式不计入预算；文档已改为单行并加断言。

feature_list.json / ledger

feature_list.json：功能级状态，只有验证通过且有证据才置 passing；id 必须唯一。

loop-ledger.json：尝试级账本。失败时 error 必填，熔断器靠它检测重复失败。

三者粒度不同，不要合并。

一次真实运行的轨迹（沙箱实测）

issue #1 → issues.opened → intake → 写 .loop/queue/issue-1.json → artifact； PR #2 转 ready → gate 阶段 → 没有 APPROVED → head-commit escalate → PR 上出现一条可读的闸门评论，Fail if escalated 让 job 失败； 故意失败的 CI → workflow_run.completed:failure → fix → 熔断 ok → 落盘； tag v0.0.1-sandbox → release → 草稿写入 step summary。
